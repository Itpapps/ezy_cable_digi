## 1. Payment Architecture Overview

The payment lifecycle is a linear, read-before-write flow. The collector never invents money values or
receipt numbers; every amount is anchored to a server-provided pending balance, and every receipt number
is issued by the backend.

```
Customer Search
   │  find the customer by a chosen criterion (name, number, mobile, etc.)
   ▼
Customer Details
   │  confirm identity; obtain the customer key used downstream
   ▼
Pending Retrieval (READ)
   │  fetch live amount owed + the billing identifier + discount/penalty context
   ▼
Payment Entry
   │  collector confirms/edits the amount to collect; chooses payment mode
   ▼
Discount Handling
   │  optional discount; amount auto-recalculates to (due − discount)
   ▼
Payment Submission (WRITE)
   │  send the full payment request to the backend
   ▼
Receipt Generation
   │  backend issues the receipt number + bill metadata in the response
   ▼
Backend Updates
   │  payment + billing records updated (immediate for STB; staged for broadband)
   ▼
Post-Payment Validation
      re-read the pending balance; confirm it changed by the amount paid
```

**Core principles (✅ verified by observed behaviour):**
- **Read before write.** The payment screen always retrieves the live pending balance first; the amount
  to collect is anchored to that value.
- **Server owns the receipt.** The receipt number is generated by the backend and returned in the
  payment response. The client never fabricates it.
- **Server owns the billing identifier.** The identifier used to settle the bill is taken from the
  Pending Retrieval response, not constructed client-side.
- **Success is gated on a status code.** A payment is only treated as successful when the response
  status code indicates success; otherwise no receipt is produced.

## 2. Customer Types

There are three payment scenarios. They differ in pending source, identifiers, settlement timing, and
discount support.

### 2.1 STB Customer

| Aspect | Behaviour | Status |
|---|---|---|
| Pending retrieval | Live amount owed returned by the Pending Retrieval operation. | ✅ |
| Billing identifier | A real, non-zero billing identifier returned by Pending Retrieval; passed back on submission. | ✅ |
| Payment processing | Synchronous — settled immediately on a successful response. | ✅ |
| Receipt generation | Receipt number issued immediately in the response (format pattern: a dealer-prefixed sequence). | ✅ |
| Database impact | A payment-detail record is created; the billing balance is reduced. | ✅ record created · 🟡 balance-reduction not yet confirmed via before/after rows |
| Discount support | Supported. Amount = due − discount. | ✅ |

### 2.2 Broadband Customer

| Aspect | Behaviour | Status |
|---|---|---|
| Pending retrieval | Broadband amount owed surfaced via a dedicated broadband pending value. | ✅ field exists · 🟡 end-to-end flow not reproduced |
| Broadband-specific fields | A broadband amount, a broadband account identifier, a broadband due value, and a renewal indicator are part of the request. | ✅ fields exist in the contract · 🟡 live values not reproduced |
| Staging / third-party processing | Asynchronous. The payment is first written to a staging area, a third-party broadband API is then called, and on success the final broadband payment record is created. | ✅ staging model confirmed · 🟡 timing/settlement not measured |
| Receipt generation | Server-issued, but on a **different format** from STB and potentially **deferred** until third-party settlement. | 🟡 |
| Database impact | A staging record first, then a separate broadband payment record on success; the billing identifier is **zero** for broadband. | ✅ staging→detail model · 🟡 exact rows not captured |
| Discount support | **Not supported** for broadband (third-party controlled). | ✅ |

### 2.3 STB + Broadband Customer

| Aspect | Behaviour | Status |
|---|---|---|
| Combined payment | A single submission can carry both an STB amount and a broadband amount. | 🟡 |
| Amount handling | STB amount and broadband amount are separate fields in the request. | ✅ separate fields exist · 🟡 combined submission not reproduced |
| Pending calculation | STB pending and broadband pending are reported separately by Pending Retrieval. | ✅ separate pending values exist |
| Receipt behaviour | Potentially two settlement paths (immediate STB + deferred broadband) → receipt timing may differ per component. | 🟡 |
| Database impact | STB tables updated immediately; broadband tables via staging. | 🟡 combined rows not captured |
| Discount behaviour | **Unverified.** Whether discount applies across the combined total, STB-only, or is blocked is not confirmed. | ⛔ |

## 5. Discount Rules

| Rule | Behaviour | Status |
|---|---|---|
| STB discount | Supported. | ✅ |
| Broadband discount | Not supported (third-party controlled). | ✅ |
| Auto-recalculation | When the collector enters a discount, the amount-to-collect field recalculates automatically. | ✅ |
| Amount formula | Amount to collect = Due − Discount. Example: due 100, discount 40 → collect 60. | ✅ |
| Discount > due | Discount cannot exceed the amount owed; the amount is clamped back to the full due. | ✅ |
| Maximum-discount cap | A maximum discount percentage limit exists and is enforced by the backend; a client-side cap also exists in the production app, driven by a login-provided limit. | ✅ exists · ⛔ client-side cap value not yet wired from login |
| Combined (STB+Broadband) discount | Whether discount applies to the combined total or STB-only is unknown. | ⛔ |

**Remaining unknowns:** the precise meaning/values of the discount/penalty flag beyond the verified
4-character value; the exact login-provided maximum-discount-percentage value and how the backend
validates it; penalty handling alongside discount.

## 8. Money Safety Requirements

These are mandatory before any release that can take real money.

1. **No fabricated receipts.** The receipt number must come only from a successful payment response. ✅ required
2. **Server-generated receipts only.** No client-side receipt-number construction, ever. ✅ required
3. **Success gated on status code.** Build/show a receipt only when the response status code = success. ✅ enforced in current behaviour
4. **No write on failure.** On any non-success status or transport error, produce no receipt and record
   no local "successful payment". ✅ enforced
5. **Double-submit protection.** The pay action must be locked while a submission is in flight and after
   a success. ✅ client guard required (server idempotency ⛔ unverified)
6. **Read-after-write validation.** After a successful payment, re-read the pending balance and confirm
   it decreased by exactly the amount paid (or shows the expected advance). ✅ required
7. **Balance verification.** Compare post-payment pending to pre-payment pending minus amount paid. ✅ required
8. **Backend consistency checks.** For broadband, confirm the staging record progresses to a settled
   payment record before treating the payment as complete. 🟡 procedure to define
9. **Test isolation.** All payment testing on a non-production/test server with a disposable customer and
   a tiny amount until sign-off. ✅ required

## 9. Implementation Plan (Phased)

> No code is written by this document. This is the sequencing plan once implementation resumes.

### Phase 1 — STB payment end-to-end
- **Dependencies:** working login/session; Pending Retrieval returning amount owed + billing identifier;
  full payment-submission request contract (§3).
- **Risks:** money mutation; partial request contracts misbehaving; discount math; double-submit.
- **Verification steps:** pay a tiny amount on a **positive-due** test customer; capture the request +
  response; confirm success status + server receipt; re-read pending (read-after-write); confirm one
  payment-detail record; compare behaviour to the production application for the same customer.
- **Acceptance criteria:** success status returned; server receipt used verbatim; pending reduced by
  exactly the amount paid; no receipt on induced failure; double submit blocked; discount math
  (due − discount) matches the production app.

### Phase 2 — Broadband payment end-to-end
- **Dependencies:** Phase 1 complete; broadband pending value + broadband fields; understanding of
  staging→third-party→settled lifecycle.
- **Risks:** asynchronous settlement; deferred/absent immediate receipt; zero billing identifier;
  no discount.
- **Verification steps:** pay a broadband test customer; confirm staging record; observe progression to a
  settled record; capture the receipt format/timing.
- **Acceptance criteria:** staging record created; settlement observed; receipt handled per its deferred
  nature; no discount path exercised.

### Phase 3 — STB + Broadband combined payment
- **Dependencies:** Phases 1 & 2 complete.
- **Risks:** mixed settlement timing; combined-amount handling; combined discount behaviour (unverified).
- **Verification steps:** combined submission on a test customer; confirm both STB and broadband records;
  capture receipt behaviour for each component.
- **Acceptance criteria:** both components settle on their respective paths; amounts reconcile;
  documented combined-discount behaviour.

### Phase 4 — Discount parity & remaining edge cases
- **Dependencies:** Phases 1–3.
- **Risks:** maximum-discount cap source value; combined-discount rules; penalty interplay; zero/advance
  customer behaviour.
- **Verification steps:** wire the login-provided maximum-discount limit; test discount at/above the cap;
  test zero-due and advance/credit customers and compare to the production app.
- **Acceptance criteria:** client-side discount cap matches the production app; zero/advance behaviour
  matches the production app; all ⛔ items in this document closed.

## 10. Release Verification Checklist (manual, pre-sign-off)

Run on a non-production/test server with a disposable customer and tiny amounts.

**STB**
- [ ] Pending Retrieval returns the correct amount owed + a billing identifier.
- [ ] Amount-to-collect prefills with the live pending balance.
- [ ] Entering a discount recalculates the amount to (due − discount); discount > due clamps to full due.
- [ ] A successful payment returns status = success and a **server-issued** receipt number.
- [ ] The on-screen/printed receipt uses the server values (receipt number, amount, bill month, dealer name).
- [ ] Re-reading pending shows it reduced by exactly the amount paid (read-after-write).
- [ ] Exactly one payment-detail record is created; no duplicates on a fast double-tap.
- [ ] Inducing a network failure mid-payment produces **no** receipt and **no** record.
- [ ] A non-success backend status shows the backend message and produces no receipt.
- [ ] Behaviour matches the production application for the same customer.

**Broadband**
- [ ] Broadband pending value retrieved correctly.
- [ ] Submission creates a staging record; settlement progresses to a final broadband record.
- [ ] Broadband receipt handled per its (possibly deferred) nature.
- [ ] No discount path is offered for broadband.

**STB + Broadband**
- [ ] Combined submission settles both components on their respective paths.
- [ ] Amounts reconcile across both components.
- [ ] Combined discount behaviour documented and matches the production app.

**Cross-cutting money safety**
- [ ] No fabricated receipts anywhere in the flow.
- [ ] Double-submit protection verified.
- [ ] No "success" recorded on any failure path.
- [ ] Maximum-discount cap enforced (client + server).
- [ ] All ⛔ gaps in this document closed and re-verified.
